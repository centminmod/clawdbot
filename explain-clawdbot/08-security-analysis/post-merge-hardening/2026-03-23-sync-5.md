#### Guard Stale Chat Buffer Sweep ([`f76e65377`](https://github.com/openclaw/openclaw/commit/f76e653776))

`startGatewayMaintenanceTimers()` in `src/gateway/server-maintenance.ts` now checks whether a run's abort controller exists before sweeping its idle chat buffers. Previously, any run idle for more than `ABORTED_RUN_TTL_MS` (60 minutes) would have its buffers cleared — including buffers for active long-running operations (tool execution, model inference) whose abort controllers were still alive. The guard adds an abort-controller presence check: only runs whose abort controller has been deleted (orphaned) are reaped; runs with live abort controllers are preserved regardless of idle time. This prevents denial-of-service via premature buffer eviction of legitimate long-running operations. The commit also introduces the `chatDeltaLastBroadcastLen` Map to track broadcast-length state needed by subsequent safety checks in the abort flow.

#### Sweep Stale chatRunState Buffers for Stuck Runs ([`550deb8c1`](https://github.com/openclaw/openclaw/commit/550deb8c18))

This is the companion fix to the abort-controller guard above. A run can reach the `ABORTED_RUN_TTL_MS` threshold without triggering a clean lifecycle end — for example, when an LLM provider times out without issuing an abort signal. Previously, buffers (`chatRunBuffers`, `chatDeltaSentAt`, `chatDeltaLastBroadcastLen`) for such stuck runs accumulated indefinitely, causing a StringAdd_CheckNone OOM crash as the Gateway tried to append to unbounded strings. The new sweep in `startGatewayMaintenanceTimers()` clears all three Maps for any run where `chatDeltaSentAt` has not been updated within `ABORTED_RUN_TTL_MS`, regardless of whether an abort was issued. Runs already present in `chatRunState.abortedRuns` are skipped to avoid double-processing by the existing aborted-run sweep.

#### Distinguish Missing Entry File from Security Violation ([`8701a224f`](https://github.com/openclaw/openclaw/commit/8701a224f8))

`resolvePackageEntrySource()` in `src/plugins/discovery.ts` now distinguishes between a plugin entry file that is missing (`"path"` or `"io"` reason from `openBoundaryFileSync` — ENOENT or IO error) and one that genuinely escapes the package directory (`"validation"` reason — path traversal). Previously, any `openBoundaryFileSync` failure was treated as a path-escape security violation, emitting the "extension entry escapes package directory" diagnostic and causing the gateway to loop on the error when a plugin's entry file was simply absent. The fix checks `opened.reason`: only `"validation"` (actual path escape) emits the security diagnostic; `"path"` (ENOENT) and `"io"` (IO error) return `null` silently. This corrects false-positive security diagnostics that prevented plugins with missing entry files from being handled gracefully, without weakening the actual path-escape detection.
